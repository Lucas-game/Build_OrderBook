上交所订单簿重建教程

代码：lob_rebuild/src/sh_stock_build_orderbook.py（沪市拼逐笔流）+ build_orderbook.py（公共：建订单簿、对账） · 数据（在 data/ 下）：SH_603353（股票）、SH_518880（ETF）、SH_110093（可转债），2026-03-02

1、我们要做什么

目标和深市一样：拿着逐笔记录，把盘口一笔一笔演出来，收盘时和交易所快照逐档对一对。

整个项目分两步，代码也按这两步分了文件：

步骤做什么代码在哪
第 1 步：拼逐笔流把委托、成交两个文件整理成同一张十列的表，排好先后各写各的：sz_stock_build_orderbook.py、sh_stock_build_orderbook.py
第 2 步：建订单簿沿逐笔流一行一行回放，改订单簿，和快照对账公共文件 build_orderbook.py

好消息是，第 2 步已经在深市写好、验证过了。说白了，沪市篇只做一件事：把沪市的两个文件，拼成一张和深市一模一样的十列逐笔流。拼好了，订单簿一行都不用改。

核心要点：沪市的难点全在第 1 步。两个交易所撮合规则一样（价格优先、时间优先），不一样的是数据怎么记录。我们要做的，是把沪市的记录方式翻译成深市的样子。

一句话：沪市篇只讲“拼逐笔流”，拼成和深市一样的十列，订单簿直接复用。

2、深市为什么简单

先回忆一下，深市拼逐笔流为什么只要几行代码。靠的是两个好性质：

  1. 有 seq。seq 是交易所发的“排队号”，委托和成交共用一套，按事件发生的先后往下发。两个文件合起来按 seq 一排，就是真实顺序，不用猜。
  2. 每张订单都有一行 ADD。哪怕它一进门就全部成交，交易所也先写一行 ADD（完整委托量），再写成交。所以回放时，成交、撤单里的订单号一定能在本子（orders 字典）里查到。

到了沪市，这两条都不成立。下面一章一章看。

一句话：深市简单，是因为有统一排队号、每单都有 ADD；沪市这两样都没有。

和深市比，有四处不同：

问题深交所上交所
撤单在哪trades.csv，被撤的一边写订单号，另一边 0，价格 0orders.csv，order_no 是被撤订单的号，自带价格和方向

还有一处藏在数据里、看几行看不出来的不同：ADD 的数量。下两章专门讲。

一句话：沪市撤单在委托文件里，没有 seq，没有委托类型，还多了 STATUS 行。

4、门卫的故事：幽灵订单

两个交易所各有一个门卫。每来一位顾客（订单），门卫要写一张“到货单”交给你，到货单就是 orders.csv 里的一行 ADD。

  • 深市门卫：每位顾客都写到货单。哪怕顾客一进门就把货全买走了，也先写到货单，再写成交单。
  • 沪市门卫：顾客一进门就全部成交的，他觉得没必要上黑板，不写到货单，只写成交单。

落到我们的变量上，记住一条规则：orders 字典只有 add_order 会写入，而 add_order 只在读到 ADD 行时才被调用。没有 ADD 行，这张订单就从没进过本子。

拿一笔沪市成交逐行走。卖单 1 先挂着 108500 × 300 股；买单 7 来了，买 100 股，一进门就吃完了，所以没有 ADD：

第 1 行 ADD   订单1 卖 108500×300
        → orders = {1: ['S', 108500, 300]}    asks = {108500: 300}

第 2 行 TRADE 买7 卖1 ×100
        → _reduce_order(7, 100)：本子里没有 7（从没写入过）→ 计数，return
        → _reduce_order(1, 100)：找到，300 → 200
        → orders = {1: ['S', 108500, 200]}    asks = {108500: 200}  ✓

最终盘口是对的：订单 7 一进门就吃完了，本来就不该在盘口上留下任何东西，跳过它正好。

核心要点：这就是为什么 _reduce_order 找不到订单号时用 return（记一笔、跳过），而不是 raise（停掉程序）。apply_trade 调了两次 _reduce_order，买方那次 return 不影响卖方那次照常扣。如果用 raise，603353 一天有两万多次这样的成交，程序第一次就停了。

实测幽灵订单数：603353 有 20,812 笔，518880 有 164,916 笔，110093（可转债）是 0 笔。

避坑指南：所以在沪市，“找不到订单号”这个计数不再是错误指标。深市它应该是 0；沪市它很大，但大部分是正常的。沪市的验收看两样：剩余量变负 = 0，十档对上。

一句话：沪市一进门就吃完的订单不留 ADD，它的订单号只在成交行里露一面，本子里自然查不到，跳过就对了。

5、剩余量：先成交后 ADD

场景再复杂一点：卖单 1 挂着 108500 × 300。买单 7 来了，要买 500 股，价格 108500，一进门吃掉 300 股，还剩 200 股挂在买盘上。

现实里的顺序就是：先成交，然后才有剩余的挂单。沪市门卫等撮合做完，看顾客还剩 200 股没买到，才补写到货单，写的是 200（剩余量），不是 500。

麻烦在于：委托和成交在两个文件里，没有共用的 seq，这两行又常常是同一毫秒。合并时如果只按时间排，很容易排反。排反了会怎样？两种顺序都走一遍：

排错：ADD 在前
行1 ADD   订单7 买 108500 qty=200  → orders[7]=200，bids={108500: 200}
行2 TRADE 买7 卖1 qty=300          → 订单7 200-300 = -100 ✗ 剩余量变负
                                      黑板 108500 扣 300 → 负数 → 被删掉
结果：bids={}  ✗  （那 200 股凭空消失了）

排对：成交在前
行1 TRADE 买7 卖1 qty=300          → 订单7 还没登记，找不到，跳过；订单1 扣完
行2 ADD   订单7 买 108500 qty=200  → orders[7]=200，bids={108500: 200}
结果：bids={108500: 200}  ✓

所以沪市股票和 ETF：成交行要排在这张订单自己的 ADD 前面。这也是沪市“找不到订单号”的第二个来源：主动单有剩余时，它的成交先到，那一刻 ADD 还没来，所以也查不到，同样是正常的。

5.1 可转债反过来

数据显示，可转债 110093 的 ADD 是完整量（500），和深市一样，所以顺序要反过来：ADD 在前，成交在后。

行1 ADD   订单7 qty=500   → bids={108500: 500}
行2 TRADE qty=300         → 订单7 剩 200，bids={108500: 200}  ✓

如果可转债硬用“成交在前”，订单 7 的 ADD 后到，登记成 500，盘口就多出 300 股。实测十档 0/10。

避坑指南：“股票、ETF 先成交后 ADD，可转债先 ADD 后成交”这条规律是从三份样本里归纳出来的，收盘对账都通过了，但没有交易所文档确认，也还没有逐张快照验证。

一句话：沪市股票和 ETF 的 ADD 写的是成交后的剩余量，所以成交要排在它自己的 ADD 前面，不然会扣多；可转债的 ADD 是完整量，顺序相反。

6、委托类型去哪了

你可能会问：沪市没有 order_type，那市价单、本方最优单怎么办？

先说事实：上交所有市价单，只是这份万得沪市数据没有提供类型这一列。但对重建来说，没有它也不影响。

回想深市为什么需要类型：深市的 ADD 是订单刚到时写的，市价单、本方最优单的价格字段不可信，要靠类型才知道它挂在哪。沪市的 ADD 是撮合之后才写的，写的是剩下的部分真正挂在哪个价格。数据里核对过：沪市所有 ADD 都带价格，没有一笔是 0。所以不管原来是什么类型，到写 ADD 的时候挂单价已经确定了，统一当 LIMIT 挂就行。

6.1 限价单也会立刻成交

卖一是 108500 × 300：

  • 买单出价 108400，够不着卖一，直接挂在买盘；
  • 买单出价 108500，够到了卖一，立刻吃掉 300 股，剩下的再挂。

上一章的买单 7 就是第二种，它是限价单。所以沪市的“幽灵订单”不只是市价单，出价够高的限价单一样可能一进门就吃完。

小技巧：本方最优单（深市的 BEST_OWN）取的是自己这一边的一档（买单取买一），而买一一定低于卖一，所以它永远不会立刻成交，只会排在本方一档后面。会立刻成交的是“对手方最优”（买单取卖一）。

一句话：沪市的 ADD 写的已经是最终挂单价，所以不需要委托类型，统一按限价挂。

7、两种号码：是谁 vs 排第几

沪市有订单号、有买卖单号，为什么还说“没有 seq”？因为它们回答的是两个不同的问题：

  • 订单号回答“是谁”，就像学号。成交行里 sell_no=182234，说明这笔成交涉及学号 182234 的那张订单。委托的 order_no ↔ 成交的 buy_no / sell_no，这是关联。回放时拿它去 orders 字典里查，不需要 pandas 的表连接。
  • seq 回答“排第几”，就像全校统一发的排队小票，不管在委托窗口还是成交窗口办事，小票号都按先后往下发。这是排序。
深市：两样都有
orders.csv  ADD   seq=7   order_no=7
trades.csv  TRADE seq=8   buy_no=7 sell_no=1        ← 7 在 8 前，不用猜

沪市：只有学号，没有排队小票
orders.csv  ADD   time=93003400  order_no=672903
trades.csv  TRADE time=93003400  buy_no=672227 sell_no=672903   ← 同一毫秒，谁先？

避坑指南：成交文件里的 trade_no 是成交自己的编号，只在成交内部连续，不能拿来和订单号比较或排序，也不能用来关联。

但订单号还有一个用处：数据核对过，ADD 的订单号随到达顺序递增（三份数据里从不倒退、不重复）；成交里订单号较大的一方是后到的主动方（和 bs_flag 在三份数据上 100% 一致）。所以订单号也能拿来当“先后”的依据，这就是第 10 章造顺序的基础。

一句话：订单号管“这笔成交说的是哪张订单”，seq 管“所有行排第几”；沪市只有订单号，所以排序得用订单号自己造。

8、整理委托

代码：sh_orders_to_tick_by_tick

和深市一样，两个文件列不同，不能直接拼，先各自整理成十列。委托文件三种行，一行一行想它进了逐笔流该长什么样：

原始行整理后为什么
STATUS丢掉不是订单
ADD 订单 2，买 463400 × 374500order_type=LIMIT，order_no=2，buy_no / sell_no 空沪市 ADD 都带真实挂单价
CANCEL B，order_no=134805order_no 空，buy_no=134805，sell_no=0装扮成深市撤单的样子

为什么撤单要“装扮”？看 apply_row 怎么处理撤单：

order_no = row.buy_no if row.side == 'B' else row.sell_no

它是从 buy_no / sell_no 里取被撤订单号的，因为深市就是这么记的。所以沪市撤单行的 order_no 要挪过去（不是删掉），order_no 留给“新委托自己的订单号”，两边含义一致，apply_row 一个字不用改。

8.1 写法：先填默认值，再按条件改

整个函数每一列都是同一个套路。用这 4 行走一遍：

   event   side  order_no
0  ADD     B     2
1  CANCEL  B     134805
2  CANCEL  S     489777
3  ADD     S     672903

第一步，造筛选条件。orders["event"] == "ADD" 逐行比较，得到一列 True/False（布尔 Series，不是 DataFrame），行号和原表对齐：

is_add = orders["event"] == "ADD"                     # True, False, False, True
cancel_buy = is_cancel & (orders["side"] == "B")      # & 是“并且”：False, True, False, False

第二步，先给整列填默认值，再用 .loc[行, 列] 改符合条件的行。.loc 逗号前选行、逗号后选列；选行的位置除了放行号，也可以放一列 True/False，表示“挑出为 True 的行”：

part["buy_no"] = pd.array([pd.NA] * n, dtype="Int64")        # 全部先填空
part.loc[cancel_buy, "buy_no"] = orders.loc[cancel_buy, "order_no"]   # 第 1 行填 134805
part.loc[cancel_buy, "sell_no"] = 0                                    # 另一边填 0

整理完：

   event   side  order_type  order_no  buy_no  sell_no
0  ADD     B     LIMIT       2         <NA>    <NA>
1  CANCEL  B                 <NA>      134805  0
2  CANCEL  S                 <NA>      0       489777
3  ADD     S     LIMIT       672903    <NA>    <NA>

避坑指南：去掉 STATUS 后，原来的行号会断开（比如少了 0）。新表 part 的行号从 0 开始，两边对不上，.loc 就会改错行。所以一开头要 reset_index(drop=True) 重新编号。

一句话：委托这边丢 STATUS、ADD 当限价、撤单把订单号挪进 buy_no / sell_no；每一列都是“先填默认值，再按条件改”。

10、拼起来，造顺序

代码：load_sh_tick_by_tick → sort_sh_tick_by_tick → add_sort_columns

先看全貌，load_sh_tick_by_tick 就四步：

orders = read_sh_orders(folder)                    # 1. 读
trades = read_sh_trades(folder)
order_part = sh_orders_to_tick_by_tick(orders)     # 2. 各自整理成十列
trade_part = sh_trades_to_tick_by_tick(trades)
tick_by_tick = pd.concat([order_part, trade_part], ignore_index=True)   # 3. 拼
return sort_sh_tick_by_tick(tick_by_tick, trade_before_add)              # 4. 排序、编 seq

和深市只差第 4 步。concat 只是上下摞起来，委托在上、成交在下，顺序是乱的。

10.1 一个真实的场景

603353，9:30:03.400 这一毫秒。卖单 672903 限价 462600，一进门当主动方，以 463300 吃掉了两笔买单；剩下 2600 股挂上卖盘；接着后来的买单 673016、673324 又吃了它。拼完、还没排序时：

CANCEL  B  134805
CANCEL  S  489777
ADD     S  672903  462600×2600      ← 委托都在上面
ADD     S  673599  463100×100
TRADE   买672227 卖672843 300
TRADE   买672227 卖672903 200       ← 672903 自己的成交，排到了它的 ADD 后面 ✗
TRADE   买672645 卖672903 200
TRADE   买673016 卖672903 800
TRADE   买673324 卖672903 100

10.2 给每一行算两个数

key：这一行在“订单号这条线”上的位置。订单号按到达顺序发，号小的在前。

  • ADD：就是这张订单本身，用自己的订单号；
  • TRADE：成交是主动方进来时发生的，用较大的订单号（主动方）；
  • CANCEL：用被撤订单号。撤单行另一边是 0，取较大值正好就是它，所以代码里 TRADE 和 CANCEL 可以一起用“较大的号”。

rank：key 撞车时谁先，数字小的在前。672903 的 ADD 和它主动吃单的成交，key 都是 672903。股票、ETF 先成交后 ADD，所以成交 0、ADD 1；撤单 2。

bigger_no = result[["buy_no", "sell_no"]].max(axis=1)   # axis=1：每一行在两列之间取较大的
result["key"] = bigger_no                               # 先全部填“较大的号”（ADD 行两边都空，结果也是空）
result.loc[is_add, "key"] = result.loc[is_add, "order_no"]   # 再把 ADD 行改成自己的订单号

rank_of = {"TRADE": 0, "ADD": 1, "CANCEL": 2}           # 对照表
result["rank"] = result["event"].map(rank_of)           # 每个 event 去表里查，换成数字

add_sort_columns 只贴这两列，不排序。

10.3 按（time, key, rank）逐级比较

result.sort_values(["time", "key", "rank"], kind="stable", ignore_index=True)

像查字典：先比 time，time 相同才比 key，key 也相同才比 rank。所以 key 只在同一毫秒里起作用，rank 只在同一毫秒、同一个 key 时起作用。排完：

                                  key      rank
CANCEL  B  134805                 134805   2    ← key 最小，排最前（rank 再大也没关系）
CANCEL  S  489777                 489777   2
TRADE   买672227 卖672843         672843   0
TRADE   买672227 卖672903         672903   0    ← 672903 主动吃单
TRADE   买672645 卖672903         672903   0
ADD     S  672903  2600           672903   1    ← 剩余量挂上去
TRADE   买673016 卖672903         673016   0    ← 后来的买单吃它（它已经是被动方）
TRADE   买673324 卖672903         673324   0
ADD     S  673599  100            673599   1

最后从 1 开始编 seq，去掉 key、rank 两列，就是和深市一样的十列逐笔流。

核心要点：排序不需要先把“先成交后 ADD”的情况找出来单独处理。对所有行用同一条规则，这种情况自然就排对了。

避坑指南：不是“所有成交排在所有 ADD 前面”。那样被动方（比如订单 672227）的 ADD 可能被排到成交后面，成交就找不到被动方了。规则只管同一毫秒里、同一个 key 的几行。

10.4 撤单为什么 rank 是 2？

撤单并不“总是最后一个”，上面的 134805 就排在最前面。rank 2 只在撞 key 时起作用，而和撤单撞 key 的只能是同一张订单的事：同一毫秒里进来、成交、被撤。一张订单还没挂上去就不可能被撤，所以撤单排在这张订单的其他事之后。

说实话：在 603353 和 518880 上，“撤单用被撤订单号当 key”和“撤单排在同一毫秒最后”两种做法结果完全一样，说明这两份数据里几乎没有“同一毫秒进来又被撤”的情况，这条规则在数据上还没被真正考验过。

一句话：用订单号给每行算位置（key），撞车时用 rank 决定谁先，按（time, key, rank）排好再编 seq。

11、trade_before_add 参数

股票、ETF 和可转债的 rank 对照表不同，靠参数 trade_before_add 区分。它从最外层一层一层往下传：

你调用：load_sh_tick_by_tick(folder, trade_before_add=True)
           ↓ 原样传下去
        sort_sh_tick_by_tick(tick_by_tick, trade_before_add)
           ↓ 原样传下去
        add_sort_columns(tick_by_tick, trade_before_add)
           ↓ 在这里才真正用来选对照表
        if trade_before_add: rank_of = {"TRADE": 0, "ADD": 1, "CANCEL": 2}
        else:                rank_of = {"ADD": 0, "TRADE": 1, "CANCEL": 2}
品种传什么
股票 603353、ETF 518880True（默认值，可以不写）
可转债 110093False（必须手动传）

避坑指南：程序不会自动判断，要靠调用的人传对。可转债如果按默认的 True 回放，收盘十档从 10/10 变成 0/10。main() 里用 SAMPLES 列表把每份数据该传的值写死了；以后可以按代码前缀自动判断（例如 110 开头是可转债）。

一句话：trade_before_add 由最外层调用时传入，中间两层原样往下传；股票、ETF 用 True，可转债传 False。

12、回放和验收

逐笔流排好了，建订单簿就直接用公共文件里的函数，一行不改：

13、回头看和下一步

回头看，沪市比深市多做的只有三件事，全在拼逐笔流这一步：

  1. 撤单从委托文件里取出来，装扮成深市撤单的样子；
  2. 没有 seq，用订单号造 key、用 rank 定撞车时谁先，排好再编 seq；
  3. 股票 / ETF 和可转债的 ADD 含义不同，用 trade_before_add 区分。

订单簿、回放、对账一行都没改，这正是“先拼逐笔流、再建订单簿”这样分层的好处。
